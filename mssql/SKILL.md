# MS SQL Server

## Safety rules — apply whenever running SQL against SQL Server, not just this project

1. **Idempotent where possible.** SQL Server has no `CREATE TABLE IF NOT EXISTS` shorthand — guard DDL with `IF OBJECT_ID('dbo.TableName', 'U') IS NULL` before `CREATE TABLE`. For idempotent seed data, use `MERGE` or an explicit `IF NOT EXISTS (SELECT 1 FROM ... WHERE ...) INSERT ...` guard instead of a plain `INSERT`.
2. **Single statement only.** Never send multiple statements separated by `;` (or on separate lines with no meaningful `GO` batch separator between them) in one execution — protects against an accidental or injected stacked statement.
3. **Timeouts.** 10s connection timeout via the connection string's `Connection Timeout=10` (ADO.NET/EF Core) or equivalent. 30s query timeout via the client-side command timeout (`SqlCommand.CommandTimeout = 30` / EF Core's configured command timeout) — SQL Server has no direct server-side per-statement execution-time cap the way MySQL's `MAX_EXECUTION_TIME` hint works, so this has to be enforced client-side. For lock waits specifically, `SET LOCK_TIMEOUT 30000;` bounds how long a statement waits on a blocked resource before erroring out.
4. **Row cap.** Use `SELECT TOP 10000 ...` (or `OFFSET 0 ROWS FETCH NEXT 10000 ROWS ONLY` if the query already has an `ORDER BY`) on ad hoc SELECT queries run for inspection/debugging.
5. **Credential protection.** Never echo a full connection string or password anywhere the output might get displayed or logged — redact before showing any command or error output.

## Lessons learned (Critical Viewer project)

- **Windows Integrated Auth is a non-starter the moment a SQL Server workload might ever run in a container or the cloud.** This project started on SQL Server with Windows Auth against a specific domain-joined server, then had to migrate fully to MySQL once the deployment target became AWS Lightsail. If there's any chance of containers/cloud down the line, design for SQL Server (username/password) auth from the start rather than assuming Windows Auth and migrating later.
- The `mcr.microsoft.com/mssql/server` image is **Linux-based** (the container's own OS reports as Ubuntu) despite "SQL Server" reading as Windows-only in most people's mental model — it's run on Linux containers for years.
- To push a locally-tagged image to a registry expecting a specific name, `docker tag mcr.microsoft.com/mssql/server:<version> <local-name>:local` is a plain rename/tag operation — no rebuild needed.
- **Efficient row-count without a table scan**: query `sys.partitions` instead of `COUNT(*)` — reads from SQL Server's internal metadata rather than scanning the table. Wired up via EF Core's `SqlQueryRaw<int?>`, aliasing the result column as `Value` so EF Core's scalar-mapping convention picks it up.
- **EF Core provider-swap gotcha in tests**: `AddDbContext` registers its configuration as an *additive* `IDbContextOptionsConfiguration<T>` service. Removing the `DbContextOptions<TContext>` registration alone is **not** enough to swap SQL Server for the InMemory provider in xUnit tests — the old SQL Server configuration is still separately registered as `IDbContextOptionsConfiguration<TContext>` and collides with the new one. Both registrations have to be removed for the swap to actually take effect.
- **Duplicate-row race under concurrent requests** (enforcing "one row per natural key" beyond what a UNIQUE constraint alone conveniently reports): pre-check for the duplicate *and* wrap the insert in `catch (DbUpdateException)` as a fallback, re-querying inside the catch block to confirm it really was a duplicate before treating it as one. A catch *filter* can't `await`, so the confirming re-query has to happen in the catch body, rethrowing if it turns out not to have been a duplicate after all.
- Used `DATETIME2(0)` (zero fractional-second precision) rather than `DATETIMEOFFSET` for timestamps — a deliberate choice when the application already normalizes everything to UTC itself and doesn't need the database to carry timezone-offset info per row.

## Lessons learned (CodeGenNew project)

- **SQL Server rejects assigning the same column twice in one `UPDATE`'s `SET` clause** — `Msg 264, Level 16: "The column name 'X' is specified more than once in the SET clause..."`. There is **no "last write wins"** behavior the way there is for repeated ordinary variable assignment. This bit a dynamically-built `UPDATE ... SET` string (a code generator assembling `SET col = ...` fragments conditionally): the design needed a column forced to a specific value under one condition, but otherwise left to whatever a caller explicitly passed — the naive approach appended *both* the caller's optional assignment fragment and a forced-override fragment for the same column, assuming the later one in the string would simply win. Instead the whole `UPDATE` statement failed outright. Fix: guarantee at most one assignment per column ever gets emitted, e.g. `IF <force-condition> SET col = <forced> ELSE IF <caller supplied a value> SET col = <caller's value>` — never two independent `IF` blocks that can both fire and both append a fragment for the same column.


## Lessons learned (CodeGenNew: exporting data and schema from SQL Server)

- `sqlcmd ... -E` can fail with "The -E and the -U/-P options are mutually exclusive" when `SQLCMDUSER`/`SQLCMDPASSWORD` are set in the environment (go-sqlcmd also trusts the Windows login by default): drop `-E` and try again.
- **Long output lines are cut by `sqlcmd`** (variable-width columns default to 256 characters; `-y 0` is refused together with `-h`; a concatenated `varchar(8000)` expression is not covered by `-y`). To export generated text (INSERT statements for another database), use **`bcp "SELECT ..." queryout file.txt -c -T -S server -d db -r '\n'`** — no width limit, one file per query. Rows with embedded newlines simply span lines.
- To copy a schema to another database, dump `sys.tables/columns/types/default_constraints`, `sys.foreign_keys(+_columns)` and `sys.indexes(+_columns)` with `sqlcmd -W -h -1 -s "|"` into small files and generate the other database's DDL from them with a script; generate the `INSERT`s with a T-SQL `SELECT` that builds the literals (`REPLACE(x, '''', '''''')`, `CONVERT(varchar(23), d, 121)`, `CASE bit WHEN 1 ...`) and run it through `bcp`.

## Lessons learned (CodeGenNew: scripts written from the catalog, 2026-10)

- **CHECK constraints:** `sys.check_constraints` joined to `sys.columns` on `parent_object_id` / `parent_column_id`. A column-level check has the column; a table-level check that mentions one column has `parent_column_id = 0`, so the column is found by reading the definition. `IN ('a','b')` is stored as an OR chain in the catalog's own order: `([s]='Closed' OR [s]='On hold' OR [s]='Open')`. Disabled checks (`is_disabled = 1`) must be skipped.
- **A key sequence table** (`GetNextID`) must lock the whole table (`WITH (TABLOCKX)`) inside its transaction, so every insert of every listed table queues behind one counter; say so next to the script. Seed each counter from `MAX(key)`.
- **Triggers that call a linked server run inside the writing statement:** an unreachable target (`Could not find server`) rolls back the user's write. `UPDATE(col)` is true when the column is in the SET list, even if the value did not change. text, ntext and image columns cannot be read from `inserted`.
- **A bulk change across tables** needs no run-time metadata walk when the script is generated: write the plain `UPDATE` per table and column.
- **Backup / restore for a scratch copy:** the service account writes the file; use the instance default backup folder (`SERVERPROPERTY('InstanceDefaultBackupPath')`) and `RESTORE FILELISTONLY` to build the `MOVE` clauses. `sqlcmd -b` plus `$LASTEXITCODE` is how a PowerShell script learns it failed.
- **History by trigger or by the engine:** an `AFTER UPDATE, DELETE` trigger reads `deleted` (before-image); `EXISTS (SELECT 1 FROM inserted)` tells update from delete. Use `SYSUTCDATETIME()` and `SUSER_SNAME()` (the login, which is a service account when the app shares one). A system-versioned table (`PERIOD FOR SYSTEM_TIME`, `SYSTEM_VERSIONING = ON (HISTORY_TABLE = ...)`) needs a primary key, keeps the history itself, and records no user; refuse a trigger-based trail on such a table. History tables carry no key, default or foreign key from the source, and `nvarchar(max)` must be declared `max`, not `(0)`.

## Lessons learned (TimeEntryServer: schema delivery, 2026-10)

- **A column cannot be made IDENTITY in place.** Rebuild the table in one transaction, with `SET XACT_ABORT ON`: `sp_rename` the table to `_old`, drop the foreign keys that point at it first (including the child's FK to it), `CREATE TABLE` the new one with `IDENTITY(1,1)` and a primary key named for the new table, `SET IDENTITY_INSERT ... ON`, `INSERT ... SELECT` with an explicit column list (so ids are kept), `OFF`, `DROP TABLE _old`, then recreate defaults, indexes and foreign keys `WITH CHECK`. Default, FK and PK names are schema-wide, so create the named defaults and FKs after the old table is dropped. Make the script re-runnable by testing `COLUMNPROPERTY(OBJECT_ID('dbo.T'), 'Col', 'IsIdentity')`, and check afterwards that `sys.foreign_keys.is_not_trusted` is 0 everywhere. Rename a misspelt column with `sp_rename 'dbo.T.Old', 'New', 'COLUMN'` (it prints a harmless "Caution" line).
- **Dynamic SQL with a variable column name:** build the statement in an `nvarchar(max)` variable first; `EXEC sp_executesql N'..' + @x + N'..'` is a syntax error.
- **Generating `schema.sql` and `seed.sql` from the catalog needs no SMO:** collect statements into `#o (ord int identity, txt nvarchar(max))` and `SELECT txt FROM #o ORDER BY ord`. Order: tables (columns from `sys.columns` + `sys.types`, `IDENTITYPROPERTY(c.object_id,'SeedValue')`), primary keys, other indexes (`sys.index_columns`, `is_included_column`, `has_filter`), defaults, checks, foreign keys, views, procedures (`sys.sql_modules.definition`, turn the first `CREATE` into `CREATE OR ALTER` with `STUFF(def, CHARINDEX(N'CREATE', def), 6, N'CREATE OR ALTER')`). Guard each object with `IF OBJECT_ID(...) IS NULL` so the script can run twice. Leave out `sysdiagrams`, `sp_*diagram*` and `fn_diagramobjects`.
- **T-SQL traps hit while doing it:** the `STRING_AGG` separator must be a literal or a variable (`N',' + @nl` is rejected: put it in `@sep`); an aggregate that mixes an outer-query column with inner columns fails with Msg 8124 (use the inner `c.object_id` in `IDENTITYPROPERTY`); a literal for dynamic SQL is easier to get right with `CHAR(39)` than with counted quotes (`'N' + CHAR(39) + REPLACE(col, CHAR(39), CHAR(39) + CHAR(39)) + CHAR(39)`).
- **A seed script that only fills empty tables** (`IF NOT EXISTS (SELECT 1 FROM T) BEGIN SET IDENTITY_INSERT T ON; INSERT ...; SET IDENTITY_INSERT T OFF; END`) is safe to run twice and never touches rows a user added. Binary columns (`image`) go out as `CONVERT(varchar(max), CONVERT(varbinary(max), col), 1)`.
- **sqlcmd output for generated text:** `-y 0` (alone, never with `-h`) prints no header line, so the output can be written to a file directly; trim trailing spaces per line and add `-f 65001` for UTF-8. Prove the pair of scripts by creating an empty database, running both twice, regenerating the schema from the result and diffing it against the original (only cosmetic `CREATE OR ALTER` spacing differed).
- **Unique name indexes** that are not filtered (`IX_Unique_*Name`) already cover a "unique among active rows" rule more strictly, but they also block reusing the name of an inactive row; say so before adding a filtered index.
