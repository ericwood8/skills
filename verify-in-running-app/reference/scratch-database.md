# Scratch database copy

Read this when: you are about to create, use or drop a disposable copy of a database (SQL Server, PostgreSQL, MySQL, Docker), or need a place where writes are safe.

Tell the user you are making a copy (creating a database on their server is an action they should know about). The harness does it: `Docs/Verification/ScratchDatabase.ps1 -Provider SqlServer|PostgreSql|MySql -Source <db> [-User <login>] [-Drop]` (creates `<db>_scratch`; PostgreSQL and MySQL need `-User`, else psql reads `-d` as the user name and reports "Ready" with no database made: check by listing `pg_database` afterwards).

The database facts behind each engine's copy (commands, privileges, errors) are in the database skills; this file is the order of work and what to check.

- **Standing SQL Server test databases:** `InvoiceSystem_test` and `TimeEntry_test` already hold a copy of the real data, the routines that write (guards on) and tagged `ZZ` fixture rows (stored bad email, -5 credit, future date, rows in use, a last page of one). For SQL Server click-throughs write to those instead of making a `_scratch` copy; rebuild with `Docs/Verification/TestDatabases/Regenerate-<Name>Test.ps1` (`-SeedOnly` re-seeds). The server is in mixed mode: `akim` and `jdoe` (limited: reader, writer, EXECUTE on dbo) connect with SQL authentication, passwords through `SQLCMDPASSWORD`; a recreated user needs `GRANT EXECUTE ON SCHEMA::dbo` again. Keep a scratch copy for the full API suites, schema changes and PostgreSQL/MySQL.
- **SQL Server copy:** copy-only backup and restore with `MOVE` to a new name; the service writes the file, so use the instance's default backup path, not a user temp folder. Details and the drop: `mssql` skill, "Backup/restore for a scratch copy". Check `$LASTEXITCODE` after each native command.
- **PostgreSQL copy:** stop every connection to the source first (a running API holds a pooled one), then `CREATE DATABASE "X_scratch" TEMPLATE "X";` (needs CREATEDB). No dump or `.bak` is left. Details: `postgres` skill, "Copying a database for a test".
- **MySQL copy:** copy the tables, or test a routine inside a rolled-back transaction when the login cannot create a database. Details: `mysql` skill, "Disposable copies and throwaway servers".
- **A throwaway Linux database:** a `mysql:8.4` container on a spare port, never the user's containers (recipe in the `mysql` skill; the saved tool `C:\Github\tools\throwaway_db.py` does it, removes only what it made, and does not pull an image without asking). Docker Desktop's engine can stop by itself, so do every check in one sitting (`docker` skill).
- **Never pipe the harness script into `Select-Object -First N`:** it stops the script upstream (a SQL Server copy was left half made, backup taken and no restore). Redirect with `*> $null` and check the database afterwards. Call it from PowerShell 7 or pass SQL to `psql` on stdin, because Windows PowerShell 5.1 loses the quotes around a mixed-case name (both explained in the `powershell` skill). List `pg_database` / `sys.databases` after every drop: a "Dropped" message can sit over a database that is still there.
- **A sample's API test project** reads the scratch connection from an environment variable (`INVOICESYSTEM_TEST_CONNECTION`); run `dotnet test` there against the copy, never the real database, unless the user says so in that message.
- PostgreSQL tables live in `public`, not `dbo` (`-s public`); `codegen -t Table -T SP_Update.tt --set "Key=Value"` generates one routine against a copy; a routine can exist twice under one name (overloads, see the `postgres` skill): drop every `pg_proc` match before applying.
- Sanity-check row counts in both databases. Passwords go in `PGPASSWORD` / `MYSQL_PWD` / environment connection strings, never a file or parameter.
- **Afterwards:** stop the servers, drop the copy, confirm only the real database remains, and re-check counts and one changed value in the **real** database. Remove your `.bak` from the backup folder if you can; otherwise tell the user where it is. Never enable `xp_cmdshell`.
