# Screens, required marks and dialogs

Read this when: you touch required marks, a WinUI3 dialog, a single-row table, a key the database does not generate, or a browser walk of generated pages.

## Required marks and WinUI3 dialog resources

- Which fields are required is one Core rule (`FormModel.IsRequired`, `IsMarked`, `ChildGrid.IsMarked`); every stack writes the literal red `*` from `RequiredMark` after the caption and flags the control itself. A web page puts the colour inline in the generated page, not in a write-once essentials file. WinUI3 draws it with a `HeaderTemplate` and sets `AutomationProperties.IsRequiredForForm` (the template and the XAML compiler trap are in the `winui3` skill, "Resources, header templates and crashes on open").
- A WinUI3 dialog that crashes on open because of a `StaticResource` on its root element: cause, fix and how to read the error are in the `winui3` skill ("Resources, header templates and crashes on open"). A build and a render test cannot see it; open the dialog (press Edit).
- To look at a WinUI3 screen, use the screenshot method in the `winui3` skill, `reference/driving-and-inspecting.md`.
- **A table shape that changes a stack's screens** (single-row tables, `SingleRowTables`): `SingleRowPlan` (Core) says which stacks and when (`Applies`; a table served as OData keeps its OData pages). A desktop stack writes the form with a template of its own (`WinUI3_SingleRowScreen`, `UNO_SingleRowScreen`, `PlanTableSet.SingleRowScreen`) that reuses the dialog's `<Table>DetailViewModel` and field XAML (the page's XAML, number formatters and handlers are `DesktopSingleRowPage` in Core, so the two templates differ only in how the row is read; a web test row and heading are `SingleRowPlan.TypeScriptRow` and `Heading`), so the dialog templates still run and `Screen` leaves the table out; a web stack lets the ordinary page template write the form (`oneRow` flag in `TSX_Page`, `TS_Component` on `SingleRowCrudScreen`, `BLZ_Page`, `BLZ_Test`), keeps the table in `ScreenForm` and out of the master-detail plan, and `WebNames` must then name the plain page (`SingleRowPlan.IsDetailMasterScreen`) or the screens file imports a page that was never written. A page that is not a view model reaches the shared context gate through `ViewModelBase.InTurnAsync`. Prove a change to a big page template with `compare_with_head.py` on a scratch project: only the essentials that gained a member may differ.
- **A key nobody generates** (a whole number with no identity, default or key-sequence table, such as a unique-index key): `FormModel.TypedKey` (text or such a number) decides the add-versus-edit behaviour of every stack, `TextKey` stays text only (sample rows and tests), `FieldKind.TypedNumberKey` is its number box (read-only after Add: `readOnly={!adding}`, `[readonly]="!adding"`, `readonly="@(!isNew)"`, `IsEnabled="{x:Bind ViewModel.IsNewRow}"`), and the entity carries `[DatabaseGenerated(None)]`. A generated React test that looks up the key field by label must look inside the dialog, because the Columns list has a check box of the same name. A WinUI3 app that closes when a page opens: read the real error as the `winui3` skill describes; a missing stored procedure (run the project's `sql` folder with `run_sql_folder.py`) looks the same as a XAML fault.
- **Browser walks (`Test-FrontEndPages.py`):** `--schema owner_scoped` generates a sign-in project (Employee user table, Expense owned by an employee, OData screens; OData cannot be combined with `Dtos`), sets passwords with the generated `set-password` command and walks each person's screen; the REST search of an owned table on the Entity Framework path is scoped, not refused. A server that answers 401 is up, so a readiness check must accept an `HTTPError`.

## App shell (menu, routes)

- **Generate the list, keep the chrome.** Only the list of screens changes per table: generate it as its own file the hand-written shell imports (React `screens.tsx`, Angular `app.routes.ts`, a WinUI3 `partial class MainWindow` with `AddScreens()`/`ShowPage()`).
